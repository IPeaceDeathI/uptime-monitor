Практический цикл «Проектирование, разработка и эксплуатация информационной системы с применением ИИ-инструментов»
Общие положения
Цель цикла – освоить на практике современные методы и инструменты создания программных продуктов: от архитектурного проектирования до развёртывания в Kubernetes с системой мониторинга, используя ИИ-ассистентов на всех этапах.
Формат – 4 практические работы
Индивидуальная тема – каждый студент выбирает одну из 30 тем (см. Приложение А) и работает с ней на протяжении всего цикла.
Требования к репозиторию – все артефакты должны быть сохранены в публичном репозитории GitHub/GitLab. 
Минимальные требования для зачёта (обязательны для всех):
3 диаграммы в нотации С4 (контекст, контейнер, компонент)
Реализация микросервисной архитектуры как минимум из двух сервисов (например, API Gateway + Business Logic Worker) с их взаимодействием (синхронным или асинхронным).
Каждый микросервис должен быть упакован в Docker-образ.
Наличие хотя бы одного внешнего хранилища (база данных, кэш, очередь сообщений) или интеграции с внешним сервисом (почта, Telegram, AI API и т.п.) – согласно выбранной теме.
Автотесты (минимум 3 сценария) для проверки основного функционала.
Развёртывание в Minikube с использованием манифестов (Deployment, Service, Ingress). 
Подключение системы мониторинга для сбора и визуализации метрик.
Дополнительные возможности для энтузиастов (поощряются, повышают оценку):
Три и более микросервиса.
Постоянное хранилище с StatefulSet (PostgreSQL, MySQL) и PVC в отдельном поде.
Применение асинхронного взаимодействия (Kafka, RabbitMQ) между сервисами.
Внедрение Service Mesh (например, Linkerd или Istio).
Развёртывание в облачном кластере (Managed Kubernetes) вместо Minikube.
Автоматизация деплоя через GitOps (ArgoCD).
Распределённая трассировка (Jaeger, Tempo) и централизованный сбор логов (Loki, ELK).
Критерии оценки (итоговая защита):
Корректность архитектуры (C4) – 4 балла
Работоспособность MVP (микросервисной версии) – 6 баллов
Автоматизация деплоя в Minikube (YAML-манифесты, работа через Ingress) – 5 баллов
Наличие и качество мониторинга (любая система, кастомные метрики) – 5 баллов.
Дифференциация оценки (баллы вместо промежуточного контроля):
Студенты, реализовавшие архитектуру сложнее минимальной (≥3 микросервисов, БД, асинхронность, Service Mesh и т.п.), получают дополнительные баллы (до +10 баллов к итоговой оценке, в зависимости от сложности).

Цели работы

Развить критическое мышление при оценке результатов работы ИИ.

Генерация диаграммы уровня Компоненты (C3): выбрать один ключевой контейнер (например, «Сервер API»), запросить у ИИ его внутреннюю структуру.

Добавить легенду и заголовок диаграммы.
Фиксация результатов:
Сохранить итоговый код PlantUML в файлы context.puml, container.puml, component.puml.
Экспортировать диаграммы в PNG (или SVG) с разрешением не менее 1200×800.

Практика №2. Реализация MVP с использованием ИИ
Цели работы
Разработать работающий прототип на выбранную тему.
Научиться использовать ИИ-агентов (Cursor, Copilot, Codeium, Claude.code и т.п.) для генерации кода, тестов и документации.
Освоить практику «промпт-инжиниринга» для ускорения разработки.
Инструменты
Среда разработки: Cursor (бесплатная версия) или VS Code с плагином Continue.dev / GitHub Copilot (студенческая лицензия) / Codeium.
Язык программирования: любой (рекомендованы Python + FastAPI, Go + Gin, TypeScript + Node.js).
Взаимодействие сервисов: HTTP/REST (через requests или aiohttp) или асинхронное через очередь (Redis, RabbitMQ).
Базы данных: PostgreSQL, SQLite, Redis – на выбор в зависимости от темы.
Очереди сообщений: Redis (pub/sub или Streams), RabbitMQ, Kafka (опционально).
Контейнеризация: Docker + docker-compose для локальной отладки.
Тестирование: pytest (Python), go test (Go), jest (Node.js) – по выбору.
Контроль версий: Git.
Минимальные требования (обязательные для всех)
Реализовать как минимум 2 микросервиса, взаимодействующих между собой (синхронно через HTTP/gRPC или асинхронно через очередь).
Хранение данных – разрешена любая БД (PostgreSQL, SQLite, in-memory – в зависимости от темы).
Обязательное наличие автотестов (интеграционных или юнит-тестов для каждого сервиса).
Использование docker-compose для локального запуска всех сервисов 
Отчёт должен включать описание того, как были использованы ИИ-агенты для генерации кода микросервисов и .yml конфига.
Дополнительные возможности (для энтузиастов)
Вынесение БД (PostgreSQL, MySQL) на отдельный микросервис в отдельном контейнере (позже это превратится в отдельный под в K8s).
Реализация асинхронных задач (через очередь сообщений) – например, генерация отчётов в фоне.

Покрытие тестами >80% кода.
Добавление фронтенда.
Интеграция с внешним API (Telegram, почта, AI)
Graceful shutdown и healthchecks во всех сервисах.

Практика №3. Контейнеризация и деплой микросервисов в Kubernetes
Цели работы
Научиться упаковывать микросервисы (из практики №2) в Docker-образы и разворачивать их в локальном кластере Minikube.
Освоить базовые объекты Kubernetes: Deployment, Service, Ingress, ConfigMap, Secret, PersistentVolumeClaim.
Получить опыт написания декларативных YAML-манифестов и управления приложением в K8s.
Инструменты
Кластер: Minikube (драйвер Docker) – минимальный вариант. Энтузиасты могут использовать облачный Managed Kubernetes (Yandex Cloud, Selectel и др.).
Управление: kubectl.
Контейнеризация: Docker 
Регистр образов: локальный реестр Minikube (minikube image load) или внешний (Docker Hub, GitHub Container Registry).
Манифесты: YAML-файлы для каждого компонента.
Минимальные требования:
Каждый микросервис из практики №2 должен быть развёрнут в отдельном Deployment (минимум 1 реплика, рекомендуется 2 для фронтенда).
Для каждого Deployment создан соответствующий Service типа ClusterIP.
Настроен Ingress для доступа к API Gateway извне (например, `myapp.local`).
Все конфигурационные параметры (URLы сервисов, пароли БД) вынесены в ConfigMap и/или Secret.
Приложение должно быть полностью работоспособно после `kubectl apply -f k8s/`.
Дополнительные возможности (для энтузиастов)
- Развёртывание базы данных (PostgreSQL, MySQL) в кластере с использованием StatefulSet и PersistentVolume.
- Настройка Horizontal Pod Autoscaler (HPA) на основе CPU.
- Использование Service Mesh (Linkerd или Istio) для наблюдения за трафиком.
- Деплой в облачный кластер (Yandex Cloud, Selectel) с публичным Ingress.
- Автоматизация через GitOps (ArgoCD). 
Ход работы
1. Подготовка образов:
   - Для каждого микросервиса проверить Dockerfile (должен быть в корне папки сервиса).
   - Загрузить образы в Minikube: `eval $(minikube docker-env)` и `docker build -t service-name:latest .`.
   - (Альтернатива) Запушить образы в Docker Hub и использовать `imagePullPolicy: Always`.

2. Создание YAML-манифестов (в папке `practice3/k8s/`):
   - `deployment-*.yaml` (для каждого сервиса)
   - `service-*.yaml` (для каждого сервиса)
   - `ingress.yaml`
   - При необходимости: `configmap.yaml`, `secret.yaml`, `pvc.yaml`, `statefulset.yaml`.

3. Запуск кластера и деплой:
   ```bash
   minikube start --driver=docker
   minikube addons enable ingress
   kubectl apply -f practice3/k8s/
   minikube tunnel   # в отдельном терминале
Проверка доступности:
Добавить в /etc/hosts строку 127.0.0.1 myapp.local.
Выполнить тестовый запрос: curl http://myapp.local/...
Диагностика:
kubectl get pods,deploy,svc,ingress
kubectl logs <pod-name>
kubectl describe pod <pod-name>
Снятие скриншотов состояния кластера и успешного ответа API.

Результаты работы:

Файл practice3/PRACTICE3.md с отчётом.

Практика №4. Мониторинг и наблюдаемость в Kubernetes
Цели работы
Развернуть систему мониторинга (на выбор) в кластере Minikube или облачном кластере.
Научиться инструментировать микросервисное приложение для экспорта метрик.
Создать информативный дашборд для отслеживания состояния приложения и кластера.
Инструменты (на выбор студента):
Prometheus + Grafana
Victoria Metrics + Grafana
SigNoz
Yandex Monitoring
Netdata
Uptrace
Zabbix
Graylog
Adminer
Другие доступные и подходящие под специфику вашего проекта

Минимальные требования (обязательны для всех):
Приложение должно экспортировать метрики на эндпоинте /metrics в формате, понятном выбранной системе (для Prometheus – открытый текст, для SigNoz – OTLP/gRPC).
Обязательные метрики:
Счётчик HTTP-запросов по эндпоинтам и кодам ответа.
Гистограмма времени ответа.
Счётчик бизнес-операций (например, passwords_generated_total).
Наличие дашборда (в Grafana, SigNoz, Netdata Cloud и т.п.), отображающего хотя бы три из указанных метрик в реальном времени.
Дополнительные возможности (для энтузиастов):
Сбор метрик с самого Kubernetes (CPU, память, сеть подов) – встроено в kube-prometheus-stack.
Настройка алертов (Alertmanager) и отправка уведомлений в Telegram или Slack или любой другой мессенджер.
Распределённая трассировка (Jaeger или Tempo) в дополнение к метрикам.
Мониторинг бизнес-показателей (например, количество активных пользователей) на отдельном дашборде.
Ход работы (на примере Prometheus + Grafana – для минимального варианта)
Установка стека мониторинга в кластер:
Добавить репозиторий Helm: helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
Установить: helm install monitoring prometheus-community/kube-prometheus-stack
Альтернативно: установить вручную через манифесты.
Инструментирование приложения:
Добавить в код каждого микросервиса экспорт метрик на эндпоинте /metrics.
Использовать клиентскую библиотеку Prometheus для вашего языка.
Пересобрать образы и обновить Deployment в кластере: kubectl rollout restart deployment/...
Настройка Prometheus для сбора метрик с приложения:
Если используется kube-prometheus-stack, добавить ServiceMonitor для сервисов приложения.
Или отредактировать ConfigMap Prometheus вручную.
Создание дашборда в Grafana:
Получить доступ к Grafana (проброс порта: kubectl port-forward svc/monitoring-grafana 3000:80).
Добавить источник данных Prometheus.
Создать дашборд с панелями (RPS, latency, бизнес-метрика).
Нагрузочное тестирование (скрипт на 100–200 запросов) и наблюдение за дашбордом.
Снятие скриншотов дашборда до и после нагрузки.
Ход работы для альтернативных систем (кратко)
Victoria Metrics: установка через Helm-чарт victoria-metrics-k8s-stack, далее аналогично Prometheus+Grafana.
SigNoz: установка через kubectl apply -f https://raw.githubusercontent.com/SigNoz/signoz/develop/deploy/kubernetes/platform/signoz.yaml, затем инструментирование приложения через OpenTelemetry SDK.
Netdata: установка через Helm-чарт netdata/netdata, получение дашборда через порт-форвард.
Результаты работы
Папка practice4/monitoring/ с файлами конфигурации (если редактировались вручную) и/или скриншотами процесса установки.
Скриншоты дашбордов (не менее 3) в practice4/screenshots/.
Отчёт practice4/PRACTICE4.md.

Какая система мониторинга выбрана и почему.
Какие метрики экспортируются приложением (названия, тип, как они помогают понять работу системы).
Как настроен сбор метрик (ServiceMonitor, статическая конфигурация, OpenTelemetry Collector и т.д.).
Ссылки на скриншоты дашборда с пояснениями каждой панели.
Результаты нагрузочного теста: как изменились метрики при росте RPS.
Вывод о пользе мониторинга для эксплуатации микросервисных систем.
